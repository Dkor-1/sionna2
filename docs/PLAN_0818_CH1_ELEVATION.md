> 사용자(2026-08-11): *"다음 팀미팅에 이 엘리베이션 실험을 **chapter 1** 으로 넣는 것이 목적이야."*
> *"구? 형태로 거리는 유지하고, 한 10 m 로 세팅."* · *"PathSolver vs SBR + PO 비교로."*

⚠ 계산이 도는 중이다. 결과가 나오면 이 문서에 실측을 채운다.

## 0. 이 장이 답하는 질문

> **드론을 올려다보는 각도가 바뀌면 마이크로도플러가 어떻게 되나. 어느 각도까지 우리 방법이 유효한가.**

지난주(8/11)는 **거리** 축이었고 우리 커널의 맵이 거의 안 변했다(상관 0.983/0.999/0.983).
그건 맞는 물리다 — 산란 진폭은 표적의 성질이고 거리는 링크버짓의 몫이다.
**앙각은 표적이 실제로 다르게 보이는 축**이라 지난주가 답 못 한 것을 답한다.

---

## 1. 설정 — 축을 하나만 바꾼다

| | |
|---|---|
| 기하 | **반경 10 m 구면**, 방위 0° 고정, 모노스태틱(baseline 0) |
| 앙각 | **0 · −15 · −30 · −45 · −60 · −75 · −90°** (7 점) |
| 표적 | matrice4e · 3.5 GHz · 4,096 자세 · PRF 19.7 kHz |
| 로터 | ⭐**8/11 덱과 같은 결정론 패턴** — OU 프리셋이 아니다 |
| 격자 | 얼린 격자(자세 합집합 bbox) · λ/12 |

⭐**구면인 것을 코드로 확인했다** — `report15_probe.place()` 가 `tx = c + R·û`, baseline 0 이라
`|tx − c| = R` 이 앙각과 무관하게 일정하다. 우리 커널도 `p_tx = ctr + range_m·û` 로 같다.

⚠**10 m 는 원거리장 경계 2D²/λ ≈ 14.08 m 안쪽**이다. 우리 커널은 `range_m` 구면파로 처리하고
PathSolver 는 실제 기하라 원래 문제없다 — 다만 **«근거리장 판»** 이라고 적어야 한다.

### 팔 둘 — ⭐**메쉬는 통째로 쓴다**

| 팔 | 무엇 |
|---|---|
| `ours` | 우리 커널(SBR + PO), **메쉬 전체** · 구면파 10 m · 얼린 격자 |
| `sionna` | PathSolver, **메쉬 전체** · 광선 (10/3)²×1M = 11,111,111 발 |

> 사용자(2026-08-11): *"mesh 는 통째로 올리고 실험하고 싶은데? **프로펠러 대역의 에너지만
> 살펴보는 게 목적**이야."*

⭐**이 판단이 옳다.** 실제 레이다가 보는 것은 동체가 붙은 온전한 드론이고, 밑에서 볼 때
동체가 로터를 가리는 것도 **답의 일부**이지 교란이 아니다. 우리가 재려는 것은
«이 드론의 프로펠러 대역 에너지가 앙각에 따라 어떻게 변하나» 이므로 메쉬를 통째로 쓴다.

⚠ 다만 대가를 적어 둔다 — 결과가 급격히 떨어질 때 **«cos(el) 때문인지 동체 가림 때문인지»
숫자로 못 가른다.** 그 분리가 필요해지면 그때 대조군을 돌린다(코드에 `--engine ours_free`
로 준비돼 있다 — 동체의 «면» 만 빼고 정점은 남겨 bbox·광선격자를 같게 유지하는 방식).
지금은 **안 돌린다.**

## 2. ⭐미리 못 박은 예측 (재기 전에 적는다)

```
f_flash = 날개 수 × 회전수 = 126.67 Hz     ← 앙각과 **무관**
f_tip   = 2·(2π f_rev R)/λ · cos(el)       ← cos(el) 로 **축소**
```

| el | f_tip [Hz] | 고정대역(430~1229)에 남는 블레이드 | 추적대역 중 창 널(563 Hz) 위 |
|---|---|---|---|
| 0° | 1273 | 100 % | 85.8 % |
| −15° (덱) | 1229 | 100 % | 83.4 % |
| −30° | 1102 | 84 % | 75.3 % |
| −45° | 900 | **59 %** | 57.6 % |
| −60° | 636 | **26 %** | **17.8 %** |
| −70.2° | 431 | **0 %** | 0 % |
| −90° | 0 | 0 % | 0 % |

### ⭐⭐ 한계가 셋이고 오는 순서가 다르다

| | 각도 | 무엇이 한계인가 | 성질 |
|---|---|---|---|
| ① | **−63.8°** | `f_tip < 563 Hz` — 블레이드가 통째로 **동체 창 누설 안**으로 | ⭐**측정 한계**(창 70 샘플이 정한다) |
| ② | **−70.2°** | `f_tip < 430 Hz` — 덱의 **고정 대역**이 완전히 빔 | 분석 선택의 한계 |
| ③ | **−90°** | 날개 속도가 시선에 **수직** → 도플러 0 | **물리 한계** |

⭐**①이 ③보다 26° 먼저 온다.** 「머리 위 드론이 안 보인다」의 실질 경계는 물리가 아니라
**우리 분석 창**이다. 창을 늘리면 밀리지만 **시간 분해능을 잃는다** — 이미 고른 트레이드오프.

## 3. 판정 게이트 — 무엇이 나와야 성공인가

| G | 무엇 | 합격선 |
|---|---|---|
| **G1** | `f_flash` 가 앙각에 **안 변한다** | 7 앙각 전부에서 126.67 ± 2 Hz (−63.8° 위 구간) |
| **G2** | `f_tip` 이 `cos(el)` 을 따른다 | 관측 대역 상단 vs 예측, 상관 ≥ 0.99 |
| **G3** | 고정 대역의 에너지가 예측대로 준다 | 표 3열과 실측 비교, ±10 %p |
| **G4** | ⭐**−63.8° 근처에서 박자 추정이 무너진다** | 그 아래에서 `beat_hz` 가 126.67 을 못 맞춤 |
| **G5** | ⭐**PathSolver 의 경로 수가 앙각에 어떻게 걸리나** | `npaths_median` 을 앙각별로 기록. 밑에서 보면 투영이 커져 늘 수도 있다 — 광선 규칙이 앙각을 안 보므로 교란 후보다 |
| **G6** | 두 엔진이 같은 방향으로 무너진다 | ①②③ 은 **측정 규약**의 성질이라 엔진에 무관해야 한다 |

⛔**어느 쪽이든 그대로 적는다.** 예측이 틀리면 그것이 더 큰 발견이다.

## 4. ⚠ 이 장이 실패할 수 있는 곳 (미리 적는다)

1. ⭐**«우리 창이 짧다» 로만 읽힐 수 있다.** 프레이밍을 정확히 해야 한다 —
   «드론이 어느 앙각에서 안 보인다» 가 **아니라** «**우리 규약이 어느 앙각까지 유효한가를 쟀다**».
   전자는 표적의 성질이라는 오해를 부르고, 후자가 실제로 한 일이다.
2. **PathSolver 의 광선 규칙이 앙각을 안 본다.** `(R/3)²×1M` 은 거리만 본다. 앙각이 바뀌면
   표적의 투영 면적이 바뀌는데 광선 수는 그대로다 — 밑에서 보면 투영이 커져 경로가 늘 수도 있다.
   **경로 수를 앙각별로 기록해서 이 교란을 드러낸다**(`npaths_median`).
3. **−90° 는 특이점이다.** f_tip = 0 이라 대역이 0 폭이 된다. 분석기가 `None` 을 내도록 했고,
   그림에서는 «측정 불가» 로 표시해야지 «0» 으로 그리면 거짓이다.
4. **7 앙각 × 2 팔 = 14 칸이라 한 장에 안 들어간다.** 슬라이드를 나누거나 앙각을 골라야 한다.
   ⭐권장: 맵은 **4 칸**(0 / −30 / −60 / −90°)만, 나머지는 **곡선 한 장**으로.
5. ⚠**8/11 덱의 대역(430~1229 Hz)을 그대로 쓰면 −45° 에서 이미 59 % 만 보고 있다.**
   그걸 모르고 쓰면 «앙각이 오르니 신호가 준다» 를 **표적 탓으로** 잘못 읽는다.
   그래서 **추적 대역과 고정 대역을 둘 다** 낸다.
