# 0967 — the same 15 m hub cells re-solved at 3.45 and 3.55 GHz, open sky and ground only, with path lists: how far is the
#        re-solved channel from the 3.5 GHz path set re-phased to the new carrier, Σ_p a_p(f0)·exp(−j2π·f·τ_p)?
#        (2026-09-18 ~14:40 KST, Package E of /workspace/sionna_queue_recommendations_2026-09-18.md §6; the 4 argument lines of
#        /workspace/sionna_gpu_queue_drafts_2026-09-18.txt «Package E» are used verbatim, unchanged.)
#
# Purpose. Every channel this project hands the CPU receiver is ray-traced once, at 3.5 GHz, and then re-phased to whatever frequency
#   the waveform needs. That step is an assumption, never tested at the settings we now use. This file tests it: 2 carriers × 2 scenes,
#   4 shards, at the cell the receiver actually reads (15 m, looking up 15°, radar on a tripod, canonical thin slab, tr38901 aimed).
#   What the result changes: if the re-solved field matches the re-phased path set inside the pre-set threshold, one 3.5 GHz ray-tracing
#   run per geometry keeps supplying every carrier inside the band, and no protocol comparison buys its own ray tracing. If it does not
#   match, the receiver's channel set is labelled «valid at 3.5 GHz only» and the next design decides how wide a band one solve covers.
#   ⛔It does not decide the carrier. The carrier is still unspecified (AGENTS.md 2026-09-18); 3.5 GHz remains a working assumption and
#   3.45 / 3.55 GHz are probes either side of it, not candidate bands.
#
# ⭐What --fc-ghz actually changes — read out of the code, not assumed. It is NOT a phase-only knob.
#   benchmark/elevation_sweep_md.py carrier() maps --fc-ghz to (fc, name tag); |fc − FC| ≤ 1 Hz returns the module constant FC
#   unchanged and adds no tag, so the stored 3.5 GHz shards are bit-identical to the untagged ones. fc then enters in FOUR places:
#   (1) scene frequency — src/scene_build.py build_scene() sets scene.frequency = fc, so every material is re-evaluated there.
#       Measured on CPU with the repo's own src/materials.material_params(): ITU concrete keeps εr = 5.240 and moves σ from
#       0.121709 to 0.124460 S/m across 3.45 → 3.55 GHz (+2.26 %); the non-ITU plastic and prop_plastic keep εr = 2.7, σ = 0.02 exactly.
#   (2) slab response — sionna/rt/utils/electromagnetics.py itu_coefficients_single_layer_slab() (ITU-R P.2040-4 eqs 43-44) builds
#       q = 2π·d/λ·sqrt(η − sin²θ), so every thickness enters only as d/λ and ±50 MHz moves d/λ by ∓1.43 %. Computed here at normal
#       incidence from that same formula (an independent recomputation, normal incidence only, so an order of magnitude and NOT a
#       prediction with a tolerance), against 3.5 GHz: 0.75 mm shell −0.124 / +0.122 dB, 1.43 mm propeller −0.122 / +0.121 dB,
#       0.30 m concrete ground +0.009 / +0.018 dB, at 3.45 / 3.55 GHz.
#   (3) wavelength scaling — sionna/rt/path_solvers/field_calculator.py multiplies every path coefficient by λ/(4π), i.e. +0.125 dB at
#       3.45 GHz and −0.123 dB at 3.55 GHz on EVERY path whatever it touches.
#   (4) propagation phase — benchmark/elevation_sweep_md.py:1147 forms E = Σ_hit a·exp(−j2π·fc·τ). This is the ONLY place it enters.
#   ⇒ (1)+(2)+(3) are exactly what a re-phasing model cannot reproduce; (4) is exactly what it does reproduce. Computed for this
#     geometry, single-bounce: λ/(4π) and one shell slab very nearly cancel (+0.125 − 0.124 = +0.001 dB at 3.45 GHz), a drone-ground
#     ghost adds the concrete term (+0.010 dB) and the radar's own nadir carries λ/(4π) plus concrete alone (+0.134 dB at 3.45,
#     −0.105 dB at 3.55). So the coefficient-only effect is expected to be SMALL and class-dependent — which is why check F1 reads it
#     per path class and not as one number.
#   What does NOT move with fc: the ray budget (--spp is given explicitly), the geometry, the pose grid (dt = 1/PRF, independent of n),
#   the blade-flash rate f_flash = 126.667 Hz. What moves but is not read here: f_tip (the merge side reads it from the _fc tag).
#   Standing reference for what closes with the λ ratio and what does not: outputs/carrier_transition_table.json — ⚠that table is
#   3.5 → 5.8 GHz (λ ratio 0.603), not ±1.4 %, and none of its numbers are quoted as a threshold here.
#
# ⭐The comparison baseline, written before anything is bought.
#   rephase_ref(f, t) = Σ_p a_p(f0, t)·exp(−j2π·f·τ_p(t)), summed over the stored 3.5 GHz path list of the SAME cell at the SAME global
#   pose index t, with f0 = 3.5 GHz exactly (the constant FC). a_p and τ_p are the sidecar's own `a` and `tau` arrays.
#   ⛔⛔THE PROPAGATION PHASE IS NOT INSIDE a_p. The sweep itself writes E = Σ a·exp(−j2π·fc·τ) at elevation_sweep_md.py:1147, and
#     jobs_0957 precondition (2) measured on CPU (4 positions, ground only, alt 5.4, tr38901, 4e6 rays) that this sum reproduces the
#     stored E and E_dedup with relative difference 0.0. So a_p is the coefficient WITHOUT exp(−j2π f τ).
#     Multiplying E, E_dedup, or any already-summed field by exp(−j2π f τ) applies that phase a second time and produces a channel
#     whose delay is twice the real one. It is a silent error: the magnitude is untouched, so |E| looks right. Check A below is what
#     catches it, and it is run on the reader as well as on the shard.
#   ⛔Never re-phase from a different cell, a different pose index, or a different seed. One cell, one pose, one seed.
