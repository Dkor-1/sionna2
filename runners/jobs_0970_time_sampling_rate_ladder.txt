# ============================================================================================================================
# WHAT THE RATE LADDER IS, AND WHAT IT IS NOT
# ============================================================================================================================
# The question. runners/jobs_0961 compared a 19,700 Hz record with a 28,029 Hz one at R15 m el -15 sky and read a linear-
#   interpolation residual of -13.11 dB, with 1.623 % of the high-rate record's AC power sitting above the 19,700 Hz Nyquist
#   (readout_0918.json gates.0961.T1_T2: interp_resid_db_linear -13.112, above_nyq_share 0.016227). That is one cell, one pair
#   of rates, and the residual cannot be split into interpolation error, solver spread and real rotor physics from two records.
#   ⛔And its two records do NOT span the same window: that gate has n_used 4,096 at both rates, so the 19,700 Hz record is
#   0.2079 s long and the 28,029 Hz one 0.1461 s - a 42 % difference in window, hence in FFT bin, on top of the rate
#   difference. ⭐This file holds the WINDOW fixed at 0.1 s and moves --n-poses with --prf instead, which is the whole design
#   point of the ladder. The same gate already gives the solver floor at that cell: seed_floor_db -1.21 dB from its
#   seed-1/seed-2 pair and rerun_floor_db -59.06 dB from a same-seed rerun - the same residual measure computed
#   between two seeds and between two runs of one seed. ⚠At that cell the two SEEDS differ by nearly as much as the signal
#   itself (-1.21 dB), so any rate residual above that value there is inside the seed spread and says nothing about rate.
#   That is why the two anchors below repeat every rate at --solver-seed 2 before any rate difference is read.
#   Every later statement about observation gaps, micro-Doppler and coherent integration rests on the time axis, so the time
#   axis is measured first, on more than one cell.
#
# HOW --prf AND --n-poses INTERACT, read from the code, not assumed.
#   benchmark/elevation_sweep_md.py:370-371 takes prf from --prf when it is > 0 and otherwise from the ledger
#   (outputs/report07_three_engines.json _meta.prf_hz = 19,700 Hz); :373 takes n from --n-poses; :405/:411 build the pose
#   times as ph = rotor_phases(np.arange(n) / prf, ...). So the time grid is t_k = k / prf for k = 0 ... n-1: the SPACING is
#   1/prf and the LENGTH is n/prf. :368 says it in the file itself - "--n-poses is record LENGTH, not sample density; the pose
#   spacing dt = 1/prf does not depend on n". Raising --n-poses alone makes a LONGER record at the same rate, not a denser one.
#   ⛔That is why every rate below carries its own --n-poses: the window is held at 0.1 s by n = round(rate x 0.1 s).
#
#   The four grids, computed here (dt = 1/prf, span = n/prf, last sample = (n-1)/prf, FFT bin = prf/n):
#   | rate [Hz] | --n-poses | dt [us]   | n/prf [s]   | last sample [s] | FFT bin [Hz] | Nyquist [Hz] |
#   |    19,700 |     1,970 |   50.7614 |   0.1000000 |       0.0999492 |     10.00000 |        9,850 |
#   |    28,029 |     2,803 |   35.6773 |   0.1000036 |       0.0999679 |      9.99964 |       14,014 |
#   |    39,400 |     3,940 |   25.3807 |   0.1000000 |       0.0999746 |     10.00000 |       19,700 |
#   |    78,800 |     7,880 |   12.6904 |   0.1000000 |       0.0999873 |     10.00000 |       39,400 |
#   Three of the four rates divide 0.1 s exactly (19,700, 39,400, 78,800 Hz).
#   28,029 Hz does not: 0.1 s x 28,029 = 2,802.9 poses, so n = 2,803 spans 0.1000036 s, which is +3.57 us
#   (+0.10 of its own sample) longer than the other three. The four records are therefore compared on the COMMON
#   window [0, 0.0999492] s - the last 19,700 Hz sample - and the 3.57e-06 s of tail beyond it is not read.
#   ⭐The property that makes the ladder readable: n/prf is the same 0.1 s at every rate, so the FFT bin is the SAME
#   10.00000 Hz at all four (column above). A spectrum or a comb-contrast difference between two rates therefore
#   cannot be a resolution difference. ⛔This is the opposite of the n-at-fixed-prf case that the runners/jobs_0965 header warns
#   about (n1024 -> 19.238 Hz bin vs n8192 -> 2.405 Hz), and it holds ONLY because --n-poses moves with --prf here.
#   ⚠What still differs across rates is the BAND, not the resolution: the comb harmonics that fit under Nyquist go from
#   9,850 Hz to 39,400 Hz. Any contrast compared across rates is computed on the common band |f| < 9,850 Hz
#   with the same harmonic set; a contrast that counts more harmonics at the high rate is not a rate comparison.
#
# WHAT MOVES IN 0.1 s, computed from src/drones.py DRONES['matrice4e'] and the ledger _meta.
#   4 rotors, 2 blades, prop diameter 274 mm, hover 3,800 rpm = 63.3333 rev/s.
#   Blade-flash rate (blades x rev/s) = 126.6667 Hz, which reproduces the ledger _meta.f_flash_hz = 126.6667 Hz.
#   Per-rotor flash rates from the ledger rpm spread: 126.945, 126.388, 126.513, 126.820 Hz, total spread
#   0.557 Hz.
#   ⛔So 0.1 s CANNOT separate the four rotors: the FFT bin is 10.000 Hz and the four flash lines lie inside
#   0.557 Hz of each other; telling them apart needs about 1.8 s. Every reading from this file is of the
#   AGGREGATE comb, and no sentence from it may name a single rotor. The per-rotor question belongs to a longer record.
#   The window holds 12.667 blade-flash periods and 6.333 rotor revolutions - neither is a whole number, so the
#   comb lines fall between bins and leak. The leakage is identical at all four rates (same bin), so it does not confound the
#   ladder; it does mean no absolute comb level from this file is quoted without its window.
#   Blade-tip Doppler, f_tip_at() at elevation_sweep_md.py:1832-1859 with c = 2.998e8: 1,268.1 Hz at el -5 deg and
#   1,229.5 Hz at el -15 deg (the ledger prints 1228.7 Hz for el -15 because it used c = 3e8).
#   ⚠f_tip is NOT the bandwidth of the record. It sits at harmonic 9.7 of the flash rate, far under even the
#   lowest Nyquist (9,850 Hz holds 77 flash harmonics). The blade flash is near-impulsive in time, so the comb runs
#   well past f_tip, and that - not the tip Doppler - is what can alias. That is exactly what 0961's 1.623 % above Nyquist says.
#
# ⛔THE HIGH RATE IS NOT "THE TRUTH".
#   78,800 Hz is the densest grid bought here and nothing more. It is one solver run with its own re-solve and seed spread,
#   it is not a converged reference, and no reading from this file may call it ground truth, the true waveform, or the exact
#   field. What the ladder can say is how a quantity MOVES as the grid is made denser, and whether that movement is larger or
#   smaller than the solver spread measured beside it. If a quantity is still moving between the two highest rates by more than
#   that spread, the honest statement is that this ladder did not reach a rate at which it stops moving - not that the top rate
#   is right. Rate is also not the only axis: runners/jobs_0961 shows the same cell moves 2.25 dB in comb contrast between
#   1e9 and 4e9 rays (gates.0961.R2), which is why the ray budget is P1's axis and is held fixed at 4e9 on every line here.
#
# ⛔A SMALL TOTAL-FIELD ERROR CAN HIDE A LARGE ROTOR-COMPONENT ERROR.
#   The hover field is dominated by the static part - the airframe body, and at the ground cells the ground-reflected classes.
#   The rotor lives in the AC part. HOW FAR below, measured by the generator on exactly the window this file reuses (the first
#   1,970 poses of the ten stored cells, both shards merged and sorted by idx; static = |mean E|^2, ac = mean|E - mean E|^2):
#   | geometry                 | seed | lvl_db      | ac_to_static_db |
#   | R15 el-15 sky            |    1 |     -119.26 |          -19.78 |
#   | R15 el-15 ground alt5.4  |    1 |     -103.59 |          -21.95 |
#   | R15 el-5  sky            |    1 |     -125.30 |          -12.40 |
#   | R15 el-5  ground alt2.81 |    1 |     -104.29 |          -23.17 |
#   | R30 el-5  sky            |    1 |     -140.42 |          -12.64 |
#   | R30 el-5  ground alt4.11 |    1 |     -105.08 |          -26.75 |
#   | R30 el-15 sky            |    1 |     -136.04 |          -16.48 |
#   | R30 el-15 ground alt9.26 |    1 |     -104.96 |          -26.88 |
#   | R15 el-15 sky            |    2 |     -118.08 |          -22.34 |
#   | R30 el-5  ground alt4.11 |    2 |     -105.07 |          -26.78 |
#   So the AC part sits 12.4 to 26.9 dB below the static part across these eight geometries. A residual quoted
#   against the TOTAL field is therefore quoted against a denominator up to 27 dB larger than the part that carries the rotor:
#   a rate error that destroys the comb entirely would still read as about -27 dB on resid_tot_db. ⛔No verdict in this file
#   is written on a total-field residual. Every residual is written twice - once relative to the total field and once relative
#   to the AC part after the per-record time mean is removed - and the AC one is the one that gates. This is the same trap the
#   repo records as "the static part leaks into the STFT band": a plausible peak built out of a quantity that never carried the
#   rotor at all. ⚠ac_to_static_db above is a property of the CELL, not a result of this file; it is written here only to size
#   the denominator problem, and the ladder's own readings are the resid_* quantities below.
#
# ⭐WHAT THIS FIXES FOR LATER: THE MASTER TIME GRID OF THE MOVING-TRAJECTORY PACKAGE (P4).
#   P4 computes 2 s episodes in which the body moves as well as the rotors, and it has to pick ONE rate for every episode,
#   every scene and every shard before any of it is computed - the campaign budgets P4 at 28,029 Hz and says so. That
#   choice is currently an assumption. This file is what turns it into a measurement: the rate at which the hover comb and the
#   path-wise coefficients stop moving, at the geometry with the fastest time variation of the eight, is the floor for P4's
#   master grid. ⚠It is a FLOOR and not the answer: P4 adds body motion, so its own Doppler bandwidth has to be added to
#   whatever this file returns, and a moving scene has to be re-profiled for cost. If this file says 28,029 Hz is not enough for
#   hover alone, P4's pose count and budget are recomputed before P4 is bought, not after.
#

# Why depth 2 everywhere, sky AND ground.
#   (1) It is the depth of the P3 representative CLI check that the campaign JSON records as dry-run passed.
#   (2) It is the depth of all eight stored comparator cells, which is what makes the whole 19,700 Hz leg reusable (REUSE).
#   (3) Depth is P1's axis, not P3's. Moving depth and rate at once would make a rate difference unreadable.
#   ⛔What that costs, stated rather than hidden: at depth 2 the ground cells carry [d], [g,d], [d,g] and [g] but NOT [g,d,g]
#   (the double ground bounce needs max_depth 3 - runners/jobs_0965 header). So this file measures the time sampling of the
#   single-bounce ground classes only, and no sentence from it may be applied to [g,d,g]. If P1 or P2 shows the double bounce
#   carries rotor modulation of its own, its rate sensitivity is a separate, later question.
#
# One shard per record (--nshards 1), on purpose. elevation_sweep_md.py:430 splits a cell as idx = np.arange(shard, n, nshards),
#   i.e. INTERLEAVED: with --nshards 2 shard 0 holds the even poses and shard 1 the odd ones, so each shard on its own is a
#   record at HALF the rate. ⛔In a package whose whole subject is the time grid, that is the one failure mode that would look
#   exactly like the effect being measured - a lost or late shard would read as a rate-halved record. With --nshards 1, idx runs
#   0 ... n-1 contiguously, t_k = k/prf directly, and no merge step sits between the solver and the time axis. The price is the
#   longest single line: about 3.4 h (R30 el-15 ground alt9.26 at 78,800 Hz), against the 0.4-0.9 h of the stored n4096
#   shards. ⚠That is longer than anything this project has run in one line; if a worker is lost the line is re-run whole.
#   --dump-paths is set equal to --n-poses on every line: :894-897 selects min(N, idx.size) evenly spaced positions, so N = n
#   with one shard dumps EVERY position. Path-wise delay and complex coefficient at common times is the point of the package,
#   so a subsampled dump would defeat it.
#
